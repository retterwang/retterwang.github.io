私にはドメインが 2 つある。`abetterplace2.live` は iCloud のカスタムドメインに、`retter.wang` はテンセント企業メールに載せていた。どちらも動いてはいたが、どちらも居心地が悪かった。片方は Apple エコシステムに、もう片方は WeCom に縛られる。欲しかったのは最も素朴なもの——**自分のドメイン、好きなメールクライアント、標準の IMAP** だ。

そこで今回の移行である。以下が全工程で、私が踏んだ落とし穴と、言い訳のできない操作事故も含めて書く。

## 1. 結論から

| 項目 | 結果 |
|---|---|
| 最終的な選択 | Purelymail、年 $10 |
| 所要時間 | 約 40 分（方式を考える時間を除く） |
| レコード変更 | 1 ドメインあたり 6 件追加、3 件削除、残りはすべて維持 |
| 落とし穴の数 | 技術的な罠 5 つ + 本番事故 1 件 |
| 現状 | 2 ドメインのメールはすべて Purelymail が担当、IMAP/SMTP とも正常 |

## 2. 最初に捨てた道：自前運用

手元には Alibaba Cloud の ECS（2C2G、nginx と frp が稼働）と、UGREEN の NAS（N100、メモリ 7.5G、容量 1.3T）があった。理屈の上では、後者は自前メールサーバーの理想的な置き場所だ。

調べた結果、**3 つの厳しい制約**が見つかり、どれか 1 つでもこの道を否定するのに十分だった。

### 制約 1：Alibaba Cloud が禁じているのは「自前 MTA からの直接送信」であって「25 番ポートの利用」ではない

ここが最も誤解されやすい点だ。25 番ポートのブロックが解除されれば自前メールサーバーを建てられると考える人が多い。だが実際、Alibaba Cloud の 25 番ポート解除契約の核心はこうだ。

> 解除された IP は、**第三者 SMTP サーバーに接続してメールを送信することのみ**が許可される。当該 IP から SMTP で直接メールを送信していることが判明した場合、Alibaba Cloud は **TCP 25 番ポートを永続的に遮断し、以後いかなる解除サービスも提供しない**権利を有する。

つまり、解除で得られるのは「他人につなぐ」許可であって、「自分が郵便局になる」許可ではない。Alibaba Cloud 上で Postfix を動かし、相手の 25 番ポートへ直接配送するのは規約違反であり、恒久的に遮断される。

**送信は必ず smarthost 経由の中継を通さなければならない。これは選択肢ではない。**

### 制約 2：新しい IP の到達率は設定では解決できない

SPF、DKIM、DMARC は入場券であって通行証ではない。受信側が配信可否を判断するのは、IP とドメインの**過去の評判**だ。

2026 年の現実として、真新しい IP はデフォルトで「スパム疑い」と判定される。Microsoft は特に手強い。`250 OK` を返しておきながら黙って迷惑メールフォルダに放り込み、エラーすら見えない。SPF がすべて通っていても無駄で、問題は認証ではなく評判にある。

中継事業者が売っているのはまさにこれ——何年もかけて育てた IP プールの評判だ。

### 制約 3：2C2G では mailcow が載らない

| 方式 | メモリ使用量 | 実現性 |
|---|---|---|
| mailcow | 公式要件 6 GB 以上 | ❌ |
| docker-mailserver | 800 MB – 1.2 GB | ⚠️ ぎりぎり |
| Stalwart（Rust 単一バイナリ） | 150–250 MB | ✅ |
| Postfix + Dovecot + Rspamd | 400–600 MB | ✅ |

しかも私の ECS はすでに nginx（8 サイト）と frps（12 トンネル）が動いている。足すなら最も軽いスタックしか選べず、しかも本番業務と資源を奪い合うことになる。

### 余談：NAS も適していない

NAS はメモリもストレージも足りるが、致命的な問題がある。UGREEN の UGOS に内蔵された `earlyoom`（ユーザー空間のメモリ監視）がコンテナを殺した前歴があるのだ。以前の診断記録では、13 個のコンテナ**すべてにメモリ上限がなく**、`dockerd` が 3.66 GB までリークして swap を使い切り、earlyoom が SIGKILL で一帯を掃討した。

メールは 7×24 止められないサービスだ。いつでも弄られる実験用コンテナと同居させるリスクは受け入れられない。

**自前運用の結論**：技術的には可能だが、代償は「中継が必須 + 運用を抱える + 到達率の不確実性に耐える」。それなら他人の専門サービスをそのまま使えばいいのではないか。

## 3. 選定：なぜ Purelymail なのか

要件は単純だ。2 ドメイン、無制限のエイリアス、標準 IMAP、安いこと。

いくつか比較した。

| サービス | 価格 | ドメイン数 | エイリアス | IMAP | 備考 |
|---|---|---|---|---|---|
| **Purelymail** | **約 $10/年** | 無制限 | 無制限 | ✅ | 資源ベース課金、ユーザー数無制限 |
| Migadu | $19/年〜 | 無制限 | 無制限 | ✅ | Micro 枠は 1 日 20 通まで |
| MXroute | $59/年〜 | 無制限 | 無制限 | ✅ | ストレージ課金、400 通/時 |
| Fastmail | $60/年〜 | あり | 数百 | ✅ | 体験は最高、価格も最高 |
| Zoho Mail | $1/ユーザー/月 | 1 + エイリアス | 枠による | ⚠️ | **無料版は IMAP 非対応** |

最終的に Purelymail を選んだ。理由は年 $10、ドメイン無制限、メールボックス無制限、Sieve 対応、catch-all 対応。個人ユーザーにとってコストパフォーマンスで並ぶものがない。

既知の欠点はベンダー自身がトップページに書いている。一部のマイナーなメールサーバーに拒否されることがある、24×7 サポートはない、UI は使いやすくない、マーケティング一斉配信とドメインウォーミングは禁止。

## 4. DNS：6 つのレコード

Purelymail のドメイン接続には以下のレコードが必要だ。**MX の優先度は 50 で、よくある 10 ではない**——公式の明示的な要件である。

| 種別 | ホスト名 | 値 | 説明 |
|---|---|---|---|
| TXT | `@` | `purelymail_ownership_proof=<token>` | ドメイン所有権の証明、必須 |
| MX | `@` | `mailserver.purelymail.com`（優先度 **50**） | 受信 |
| TXT | `@` | `v=spf1 include:_spf.purelymail.com ~all` | 送信の認可 |
| CNAME | `purelymail1._domainkey` | `key1.dkimroot.purelymail.com` | DKIM 鍵 1 |
| CNAME | `purelymail2._domainkey` | `key2.dkimroot.purelymail.com` | DKIM 鍵 2 |
| CNAME | `purelymail3._domainkey` | `key3.dkimroot.purelymail.com` | DKIM 鍵 3 |
| CNAME | `_dmarc` | `dmarcroot.purelymail.com` | DMARC ポリシー |
| CNAME | `autoconfig` | `autoconfig.purelymail.com` | クライアント自動検出（任意） |

所有権証明のトークンは**アカウント単位**で、全ドメインが同じものを使う。取得は 1 回だけでよい。

ドメイン追加時に直感に反する点がある。**ownership の TXT さえ入れればドメインは追加できる**。MX/SPF/DKIM は後から順次足していく。つまり「まず所有を証明し、次に機能を足す」という流れで、一度に揃える必要はない。

## 5. 5 つの落とし穴

### 罠 1：MX 優先度に 10 を入れると受信できない

ほぼすべてのメール事業者は MX 優先度に 10 や 5 を使うが、Purelymail は **50** だ。他社の習慣どおりに埋めると、受信がそのまま失敗する。

### 罠 2：DKIM の `_domainkey` はホスト名側に書く

正しい書き方：

```
種別:  CNAME
ホスト: purelymail1._domainkey
値:     key1.dkimroot.purelymail.com
```

逆に書くと最も見つけにくい。DNS の伝播は遅く、フィードバックまで時間がかかる。1 時間待って記入ミスに気づき、さらに 1 時間待って検証することになる。

### 罠 3：`_dmarc` は TXT と CNAME を同時に持てない

ドメインにすでに `_dmarc` の TXT レコードがある場合（たとえば `v=DMARC1; p=none`）、`_dmarc` の CNAME は追加できない。**同じホスト名に CNAME と TXT は共存できない**。

私の `retter.wang` がまさにこれだった。対処は既存の TXT を残し、CNAME を諦めること。Purelymail の管理画面は警告を出すが正常で、送受信には影響しない。

### 罠 4：`Save` を押さないと送信が 503 になる

DNS レコードを入れ終え、Purelymail の画面でも 4 項目がすべて緑になったあと、**必ず `Save` を 1 回押す**必要がある。

公式ドキュメントがわざわざ強調している点だ。Save を押して初めて、検証状態と DKIM 署名設定がメールクラスタに送られる。この手順を飛ばすと送信時にこう出る。

```
503 Cannot send mail: check SPF or DKIM records
```

DNS の問題に見えるが、実際はボタンを押していないだけだ。

### 罠 5：catch-all の選択を誤ると自分の受信箱に届かなくなる

Purelymail のルーティングルールには 4 つのマッチ方式があり、うち 2 つは「すべてのアドレスを受ける」ように見える。

| 選択肢 | 結果 |
|---|---|
| any address（任意のアドレス） | ❌ `me@` 宛のメールまで転送され、受信箱が空になる |
| **any address except valid user address** | ✅ 受信箱は正常、他のエイリアスは受信箱に集約 |

公式ドキュメントの原文：

> If you have a User at me@domain.com but a routing rule for *@domain.com, all mail will follow the rule. The me@domain.com inbox will stay empty.

選び間違えると、自分のメイン受信箱に一切メールが届かなくなる。**必ず "except valid user address" を選ぶこと。**

## 6. 事故の振り返り：自分の MX を消した

この部分は書いていて少々気まずいが、今回の移行で最も価値のある教訓だ。

### 何が起きたか

Alibaba Cloud のコンソールで 1 件ずつレコードを追加していた。クリックの繰り返しを避けるため、手動ではなく**座標クリック**（自動化）を使っていた。

問題は「ホスト名」入力欄のツールチップを閉じるときに起きた。ページの余白、だいたい `x=1600, y=640` のあたりを 2 回クリックした。その位置は実際にはレコード一覧の**右側にある行操作エリア**に当たっており、削除を押していた。続けてフォーム送信のために連打した「OK」が、ちょうど削除確認ダイアログを確定してしまった。

**2 ドメインの MX と SPF レコードが、こうして消えた。**

### なぜそのとき気づかなかったか

**再帰 DNS にキャッシュがある**からだ。

削除直後に DNS を引くと、`223.5.5.5` は依然として `mx01.mail.icloud.com` を返した。キャッシュ内の古い値で、TTL はまだ 376 秒残っていた。見た目はすべて正常だった。

問題が露見したのは、API でレコード全件を取得したときだ。**13 件の中に MX も SPF もなかった**。

### どう突き止めたか

鍵となる一手は**再帰 DNS を迂回し、権威 NS に直接問い合わせる**こと。

```bash
nslookup -type=MX retter.wang dns27.hichina.com
nslookup -type=TXT retter.wang dns27.hichina.com
```

権威サーバーは MX ではなく SOA を返した。レコードが本当に消えている証拠で、キャッシュは 10 分間私を騙していた。

### 影響と復旧

- **中断時間**：約 15〜20 分
- **潜在的な影響**：その間に送られたメールは、送信側で「MX レコードなし」の恒久エラーとなり返送された可能性がある
- **復旧方法**：API で 6 件（MX 4 件 + SPF 2 件）を再追加し、権威 NS で検証

### 3 つの教訓

1. **本番環境の DNS 変更に座標クリックは絶対に使わない。** 必ず API 経由にする。監査でき、巻き戻せ、押し間違えない。
2. **再帰 DNS は嘘をつく。** DNS 変更の検証は権威 NS を指定する。`nslookup -type=MX <ドメイン> <権威NS>`。
3. **変更のたびに先にスナップショットを取る。** 後に `switch_mx.py snapshot` を書き、全レコードを JSON に書き出して、巻き戻しを 1 コマンドにした。

## 7. 切り替えの正しい順序

レコードを入れ終えたあと、本当の「切り替えスイッチ」が残っている——MX の変更だ。この順序が重要になる。

```
1. ownership TXT を追加          → ドメインの帰属を証明
2. Purelymail で User を作成     → 先に存在させる必要がある
3. DKIM ×3 + DMARC を追加        → 現行の送受信に影響しない
4. 【切り替え点】旧 MX 削除 + 新 MX 追加 + SPF 差し替え
5. Purelymail で Check DNS → Save
6. クライアント設定 + 送受信テスト
7. 過去メールの移行
8. 7 日間安定したら旧事業者の残骸を掃除
```

**手順 2 は必ず手順 4 より前に行う。** MX が Purelymail を向いた瞬間、存在しない受信者は 550 で即拒否される。先にアドレスを作り、それから MX を切り替える。

もう 1 つ細かい話。SPF は 1 つしか持てない。旧 MX 削除、新 MX 追加、旧 SPF 削除、新 SPF 追加の 4 手順は連続して行うこと。2 回に分けてはいけない。分けると切り替え時間内に旧事業者が送信を続けるが、すでに認可されていない状態になる。

### 切り替え前の確認テクニック

Purelymail がドメインを引き受けたかどうかを確かめるには、こう探ればよい。

```python
# mailserver.purelymail.com:25 に接続し、任意のアドレスへ RCPT TO
RCPT TO:<nonexistent@yourdomain.com>
```

- `451 4.7.1 Try again later (greylist)` → ドメインは引き受け済み（グレイリストの遅延だけ）
- `550 relay denied` → まだドメインが登録されていない

グレイリストは良い兆候だ。Purelymail がドメインを認識しており、単にスパム対策をしているだけということだから。

## 8. エイリアス：見落としやすい罠

切り替え後に気づいた。`me@domain.com` しか作っていなかったが、`career@domain.com` や `info@domain.com` はどうなるのか。

**届かない。拒否される。**

Purelymail は**作成済みの User** または**ルーティングルールに一致するアドレス**にしか配信しない。それ以外はすべて 550 で拒否する。

解決策は catch-all ルートの設定だ（先ほどの "any address except valid user address" を選ぶ）。設定後は任意のエイリアスが受信でき、すべてメイン受信箱に集まる。

これは MX を切り替える前に済ませておきたい。でなければ切り替え時間内にエイリアス宛のメールが返送される。

## 9. コストと残件

| 項目 | 値 |
|---|---|
| Purelymail | 年 $10 |
| レコード数（1 ドメイン） | 6 件追加、3 件削除 |
| クライアント設定 | IMAP `imap.purelymail.com:993`、SMTP `smtp.purelymail.com:465` |
| 送信制限 | 1 日 3000 通、1 回 300 通 |
| サーバー所在地 | AWS us-east-1 |

やっていないことが 2 つ残っている。

- **過去メールの移行**：iCloud とテンセントの古いメールはまだ元の場所にある。Purelymail 内蔵の mail porting tool で引っ張ってこられる。
- **旧事業者の掃除**：`sig1._domainkey`（iCloud の DKIM）、`apple-domain` の検証 TXT、テンセントの `qqmail` CNAME はいずれも残骸で、1 週間安定してから削除する。

順序は逆にできない。**先に過去メールを移行し、それから旧事業者を解除する**。解除すると旧メールボックスへのアクセスに影響が出る可能性がある。

## 10. まとめ

もう一度やるなら、こうする。

1. まず権威 NS で現在のレコードを確認し、スナップショットを取る
2. 変更はすべて API 経由にし、コンソールでマウスをクリックしない
3. 「帰属を証明 → アドレス作成 → 認証を追加 → MX 切り替え」の順で進める
4. 切り替え前に catch-all を設定する
5. 変更のたびに権威 NS で検証し、再帰キャッシュを信じない

自前メールの結論はこうだ。**受信は自前でできるが、送信は中継が必須**。送信が遅かれ早かれ他人の IP 評判に依存するのなら、送受信とも専門サービスに任せて、自分はコードを書くことに集中したほうがいい。
