도메인 메일 이전 기록: iCloud + 텐센트 기업 메일에서 Purelymail로

2026년 11월 17일 약 2분 AIGC

제게는 도메인이 두 개 있습니다. abetterplace2.live는 iCloud 사용자 도메인에, retter.wang은 텐센트 기업 메일에 붙여 두었습니다. 둘 다 쓸 수는 있었지만 둘 다 불편했습니다. 하나는 애플 생태계에, 다른 하나는 WeCom에 묶여 있었으니까요. 제가 원한 것은 가장 소박한 것이었습니다. 내 도메인, 아무 메일 클라이언트, 표준 IMAP.

그래서 이전을 진행했습니다. 아래는 전체 과정이며, 제가 밟은 함정과 용서할 수 없는 운영 사고까지 담았습니다.

1. 결론부터

항목 결과
최종 선택 Purelymail, 연 $10
소요 시간 약 40분 (방식을 고민한 시간 제외)
레코드 변경 도메인당 6개 추가, 3개 삭제, 나머지는 모두 유지
함정 개수 기술적 함정 5개 + 운영 사고 1건
현재 상태 두 도메인 메일 전부 Purelymail이 담당, IMAP/SMTP 정상

2. 먼저 포기한 길: 직접 구축

손에는 알리바바 클라우드 ECS(2C2G, nginx와 frp 구동 중)와 UGREEN NAS(N100, 메모리 7.5G, 저장 공간 1.3T)가 있었습니다. 이론적으로 후자는 자체 메일 서버를 두기에 이상적인 환경입니다.

조사해 보니 세 가지 강한 제약이 나왔고, 어느 하나만으로도 이 길은 무너집니다.

제약 1: 알리바바 클라우드가 금지하는 것은 "자체 MTA 직접 발송"이지 "25번 포트 사용"이 아니다

가장 흔히 오해되는 부분입니다. 25번 포트 차단만 풀면 자체 메일 서버를 세울 수 있다고 생각하기 쉽습니다. 하지만 실제로 알리바바 클라우드의 25번 포트 해제 계약 핵심 조항은 이렇습니다.

해제된 IP는 제3자 SMTP 서버에 접속해 메일을 발송하는 것만 허용된다. 해당 IP에서 SMTP로 직접 메일을 발송하는 것이 확인되면, 알리바바 클라우드는 TCP 25번 포트를 영구 차단하고 이후 어떤 해제 서비스도 제공하지 않을 권리를 가진다.

즉, 해제로 얻는 것은 "남에게 접속할" 허가이지 "내가 우체국이 될" 허가가 아닙니다. 알리바바 클라우드에서 Postfix를 돌려 상대의 25번 포트로 직접 배달하는 것은 규약 위반이며 영구 차단됩니다.

발송은 반드시 smarthost 릴레이를 거쳐야 합니다. 선택 사항이 아닙니다.

제약 2: 새 IP의 전달률은 설정으로 해결되지 않는다

SPF, DKIM, DMARC는 입장권이지 통행증이 아닙니다. 수신 측이 배달 여부를 판단할 때 보는 것은 IP와 도메인의 과거 평판입니다.

2026년의 현실은 이렇습니다. 완전히 새 IP는 기본 판정이 "스팸 의심"입니다. Microsoft는 특히 까다로워서 250 OK를 돌려주고는 조용히 스팸함에 넣어 버리고, 오류조차 보이지 않습니다. SPF가 모두 통과해도 소용없습니다. 문제는 인증이 아니라 평판이니까요.

릴레이 업체가 파는 것이 바로 이것입니다. 몇 년에 걸쳐 길러 낸 IP 풀의 평판 말입니다.

제약 3: 2C2G에는 mailcow가 들어가지 않는다

방식 메모리 사용량 실현성
mailcow 공식 요구 6 GB 이상 ❌
docker-mailserver 800 MB – 1.2 GB ⚠️ 간신히
Stalwart (Rust 단일 바이너리) 150–250 MB ✅
Postfix + Dovecot + Rspamd 400–600 MB ✅

게다가 제 ECS는 이미 nginx(사이트 8개)와 frps(터널 12개)가 돌고 있습니다. 얹으려면 가장 가벼운 스택을 골라야 하고, 운영 업무와 자원을 다퉈야 합니다.

참고로 NAS도 적합하지 않다

NAS는 메모리와 저장 공간이 충분하지만 치명적인 문제가 있습니다. UGREEN UGOS에 내장된 earlyoom(사용자 공간 메모리 감시)이 컨테이너를 죽인 전력이 있다는 점입니다. 이전 진단 기록을 보면 컨테이너 13개 모두 메모리 상한이 없었고, dockerd가 3.66 GB까지 누수해 swap을 모두 채우자 earlyoom이 SIGKILL로 광범위하게 정리해 버렸습니다.

메일은 7×24 중단될 수 없는 서비스입니다. 수시로 건드리는 실험용 컨테이너와 같이 두는 위험은 받아들일 수 없습니다.

직접 구축의 결론: 기술적으로는 가능하지만 대가는 "릴레이 필수 + 운영 부담 + 전달률 불확실성 감수"입니다. 그럴 바에야 남의 전문 서비스를 그냥 쓰는 편이 낫지 않을까요.

3. 선택: 왜 Purelymail인가

요구 사항은 단순했습니다. 도메인 두 개, 무제한 별칭, 표준 IMAP, 저렴한 가격.

몇 곳을 비교했습니다.

서비스 가격 도메인 수 별칭 IMAP 비고
Purelymail 연 약 $10 무제한 무제한 ✅ 자원 기반 과금, 사용자 수 무제한
Migadu 연 $19부터 무제한 무제한 ✅ Micro 등급은 하루 20통까지만 발송
MXroute 연 $59부터 무제한 무제한 ✅ 저장 공간 기준 과금, 시간당 400통
Fastmail 연 $60부터 지원 수백 개 ✅ 경험이 가장 좋고 가격도 가장 높음
Zoho Mail 사용자당 월 $1 1 + 별칭 등급별 ⚠️ 무료판은 IMAP 미지원

결국 Purelymail을 골랐습니다. 연 $10, 도메인 무제한, 메일함 무제한, Sieve 지원, catch-all 지원. 개인 사용자에게 이만한 가성비는 없습니다.

알려진 단점은 업체가 직접 첫 페이지에 적어 두었습니다. 일부 마이너 메일 서버가 가끔 수신을 거부하고, 24×7 지원이 없고, UI가 그리 편하지 않고, 마케팅 대량 발송과 도메인 워밍이 금지됩니다.

4. DNS: 레코드 여섯 개

Purelymail에 도메인을 연결하려면 다음 레코드가 필요합니다. MX 우선순위는 흔한 10이 아니라 50이라는 점에 주의하세요. 공식 요구 사항입니다.

유형 호스트 값 설명
TXT @ purelymail_ownership_proof=<token> 도메인 소유권 증명, 필수
MX @ mailserver.purelymail.com (우선순위 50) 수신
TXT @ v=spf1 include:_spf.purelymail.com ~all 발송 인가
CNAME purelymail1._domainkey key1.dkimroot.purelymail.com DKIM 키 1
CNAME purelymail2._domainkey key2.dkimroot.purelymail.com DKIM 키 2
CNAME purelymail3._domainkey key3.dkimroot.purelymail.com DKIM 키 3
CNAME _dmarc dmarcroot.purelymail.com DMARC 정책
CNAME autoconfig autoconfig.purelymail.com 클라이언트 자동 검색 (선택)

소유권 증명 토큰은 계정 단위라 모든 도메인이 같은 값을 공유합니다. 한 번만 가져오면 됩니다.

도메인을 추가할 때 직관에 반하는 점이 하나 있습니다. ownership TXT만 넣으면 도메인이 추가됩니다. MX/SPF/DKIM은 이후에 차례로 채우면 됩니다. 즉 "먼저 소유를 증명하고, 다음에 기능을 붙인다"는 흐름이고, 한 번에 다 갖출 필요가 없습니다.

5. 다섯 개의 함정

함정 1: MX 우선순위에 10을 넣으면 수신이 안 된다

거의 모든 메일 사업자가 MX 우선순위로 10이나 5를 쓰지만 Purelymail은 50입니다. 남의 관습대로 채우면 수신이 그대로 실패합니다.

함정 2: DKIM의 _domainkey는 호스트 이름 쪽에 쓴다

올바른 표기:

유형:  CNAME
호스트: purelymail1._domainkey
값:     key1.dkimroot.purelymail.com

반대로 쓰면 찾기 가장 어렵습니다. DNS 전파가 느리고 피드백 주기가 깁니다. 한 시간 기다려 오타를 발견하고, 다시 한 시간 기다려 검증하게 됩니다.

함정 3: _dmarc는 TXT와 CNAME을 동시에 가질 수 없다

도메인에 이미 _dmarc TXT 레코드가 있다면(예: v=DMARC1; p=none) _dmarc CNAME을 추가할 수 없습니다. 같은 호스트 이름에 CNAME과 TXT가 함께 존재할 수 없습니다.

제 retter.wang이 바로 이 경우였습니다. 처리 방식은 기존 TXT를 유지하고 CNAME을 건너뛰는 것입니다. Purelymail 관리 화면에 경고가 뜨지만 정상이며 송수신에는 영향이 없습니다.

함정 4: Save를 누르지 않으면 발송이 503으로 실패한다

DNS 레코드를 다 넣고 Purelymail 화면에서 네 항목이 모두 초록이 된 뒤에도, 반드시 Save를 한 번 눌러야 합니다.

공식 문서가 따로 강조하는 부분입니다. Save를 눌러야 검증 상태와 DKIM 서명 설정이 메일 클러스터로 전달됩니다. 이 단계를 건너뛰면 발송 시 이렇게 나옵니다.

503 Cannot send mail: check SPF or DKIM records

DNS 문제처럼 보이지만 실제로는 버튼을 누르지 않은 것입니다.

함정 5: catch-all 옵션을 잘못 고르면 내 메일함이 비어 버린다

Purelymail 라우팅 규칙에는 네 가지 매칭 방식이 있고, 그중 두 가지는 "모든 주소를 받는다"처럼 보입니다.

옵션 결과
any address (모든 주소) ❌ me@ 자신에게 온 메일까지 리다이렉트되어 메인 메일함이 빈다
any address except valid user address ✅ 메인 메일함은 정상, 나머지 별칭은 메인으로 모임

공식 문서 원문:

If you have a User at me@domain.com but a routing rule for *@domain.com, all mail will follow the rule. The me@domain.com inbox will stay empty.

잘못 고르면 내 주 메일함으로 아무 메일도 오지 않습니다. 반드시 "except valid user address"를 골라야 합니다.

6. 사고 회고: 제 MX를 제가 지웠습니다

이 부분은 쓰기 조금 민망하지만, 이번 이전에서 가장 값진 교훈입니다.

무슨 일이 있었나

알리바바 클라우드 콘솔에서 레코드를 하나씩 추가하고 있었습니다. 반복 클릭을 피하려고 수동 클릭이 아니라 좌표 클릭(자동화)을 사용했습니다.

문제는 "호스트 레코드" 입력란의 툴팁을 닫을 때 생겼습니다. 페이지 여백, 대략 x=1600, y=640 지점을 두 번 클릭했습니다. 그 위치가 실제로는 레코드 목록 오른쪽의 행 작업 영역에 떨어져 삭제를 눌러 버렸습니다. 이어서 폼을 제출하려고 연달아 누른 "확인"이 마침 삭제 확인 창을 승인했습니다.

두 도메인의 MX와 SPF 레코드가 그렇게 사라졌습니다.

왜 그때 몰랐나

재귀 DNS에 캐시가 있기 때문입니다.

삭제 직후 DNS를 조회하니 223.5.5.5는 여전히 mx01.mail.icloud.com을 반환했습니다. 캐시에 남은 옛 값이었고 TTL이 376초 남아 있었습니다. 겉보기에는 모두 정상이었습니다.

문제가 드러난 것은 API로 전체 레코드 목록을 가져왔을 때입니다. 13개 레코드에 MX도 SPF도 없었습니다.

어떻게 찾아냈나

핵심은 재귀 DNS를 우회해 권한 NS에 직접 묻는 것이었습니다.

nslookup -type=MX retter.wang dns27.hichina.com
nslookup -type=TXT retter.wang dns27.hichina.com

권한 서버가 MX가 아니라 SOA를 반환했습니다. 레코드가 정말로 사라졌다는 증거였고, 캐시가 10분 동안 저를 속인 것입니다.

영향과 복구

  • 중단 구간: 약 15–20분
  • 잠재적 영향: 그 구간에 발송된 메일은 발신 측에서 "MX 레코드 없음" 영구 오류로 반송되었을 수 있음
  • 복구 방법: API로 6개 레코드(4 MX + 2 SPF)를 다시 추가하고 권한 NS로 검증

세 가지 교훈

  1. 운영 환경의 DNS 변경에 좌표 클릭을 절대 쓰지 않는다. 반드시 API로 처리한다. 감사 가능하고, 되돌릴 수 있고, 잘못 누르지 않는다.
  2. 재귀 DNS는 거짓말을 한다. DNS 변경 검증은 권한 NS를 지정해야 한다. nslookup -type=MX <도메인> <권한NS>.
  3. 변경 전에 항상 스냅숏을 뜬다. 이후 switch_mx.py snapshot을 만들어 전체 레코드를 JSON으로 내보내고, 되돌리기를 명령 한 줄로 만들었다.

7. 전환의 올바른 순서

레코드를 다 넣은 뒤에도 진짜 "전환 스위치"가 남아 있습니다. MX를 바꾸는 일입니다. 이 순서가 관건입니다.

1. ownership TXT 추가          → 도메인 소유 증명
2. Purelymail에서 User 생성     → 먼저 존재해야 함
3. DKIM ×3 + DMARC 추가        → 기존 송수신에 영향 없음
4. 【전환 지점】옛 MX 삭제 + 새 MX 추가 + SPF 교체
5. Purelymail에서 Check DNS → Save
6. 클라이언트 설정 + 송수신 테스트
7. 지난 메일 이전
8. 7일 안정화 후 옛 사업자 잔여물 정리

2단계는 반드시 4단계보다 앞서야 합니다. MX가 Purelymail을 가리키는 순간 존재하지 않는 수신자는 곧바로 550으로 거부됩니다. 주소를 먼저 만들고 MX를 바꾸세요.

또 하나의 세부 사항. SPF는 하나만 가질 수 있습니다. 옛 MX 삭제, 새 MX 추가, 옛 SPF 삭제, 새 SPF 추가의 네 단계는 연속으로 끝내야 하며 두 번에 나눠서는 안 됩니다. 나누면 전환 구간에 옛 사업자가 여전히 발송하지만 더는 인가되지 않은 상태가 됩니다.

전환 전 확인 요령

Purelymail이 도메인을 넘겨받았는지 확인하려면 이렇게 탐침하면 됩니다.

# mailserver.purelymail.com:25에 접속해 임의 주소로 RCPT TO
RCPT TO:<nonexistent@yourdomain.com>
  • 451 4.7.1 Try again later (greylist) → 도메인 인수 완료 (그레이리스트 지연일 뿐)
  • 550 relay denied → 도메인이 아직 등록되지 않음

그레이리스트는 좋은 신호입니다. Purelymail이 도메인을 인식하고 있고 단지 스팸을 거르는 중이라는 뜻이니까요.

8. 별칭: 놓치기 쉬운 함정

전환을 마치고 문제를 하나 발견했습니다. me@domain.com 하나만 만들었는데 career@domain.com, info@domain.com은 어떻게 되는 걸까요.

오지 않습니다. 거부됩니다.

Purelymail은 이미 만든 User 또는 라우팅 규칙에 맞는 주소로만 배달합니다. 나머지는 모두 550으로 거부합니다.

해결책은 catch-all 라우팅 설정입니다(앞서 말한 "any address except valid user address" 옵션). 설정하면 어떤 별칭으로 와도 수신되어 모두 메인 메일함으로 모입니다.

이 작업은 MX를 바꾸기 전에 끝내 두는 편이 좋습니다. 그러지 않으면 전환 구간에 별칭으로 온 메일이 반송됩니다.

9. 비용과 남은 일

항목 값
Purelymail 연 $10
레코드 수(도메인당) 6개 추가, 3개 삭제
클라이언트 설정 IMAP imap.purelymail.com:993, SMTP smtp.purelymail.com:465
발송 한도 하루 3000통, 1회 300통
서버 위치 AWS us-east-1

아직 하지 않은 일이 두 가지 있습니다.

  • 지난 메일 이전: iCloud와 텐센트의 옛 메일은 아직 원래 자리에 있습니다. Purelymail 내장 mail porting tool로 가져올 수 있습니다.
  • 옛 사업자 정리: sig1._domainkey(iCloud DKIM), apple-domain 검증 TXT, 텐센트의 qqmail CNAME은 모두 잔여물이라 일주일 안정화 후 삭제합니다.

순서는 뒤집을 수 없습니다. 지난 메일을 먼저 이전하고, 그다음 옛 사업자를 해제합니다. 해제하면 옛 메일함 접근이 영향을 받을 수 있습니다.

10. 정리

다시 한다면 이렇게 하겠습니다.

  1. 먼저 권한 NS로 현재 레코드를 확인하고 스냅숏을 뜬다
  2. 모든 변경은 API로 처리하고 콘솔에서 마우스를 클릭하지 않는다
  3. "소유 증명 → 주소 생성 → 인증 추가 → MX 전환" 순서로 진행한다
  4. 전환 전에 catch-all을 설정한다
  5. 변경할 때마다 권한 NS로 검증하고 재귀 캐시를 믿지 않는다

자체 메일함의 결론은 이렇습니다. 수신은 직접 구축할 수 있지만 발송은 릴레이가 필수입니다. 발송이 결국 남의 IP 평판에 기대야 한다면, 송수신 모두 전문 서비스에 맡기고 자신은 코드에 집중하는 편이 낫습니다.

아낀 시간이면 글을 몇 편 더 쓸 수 있습니다.
